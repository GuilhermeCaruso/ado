# index-service

Analyzes the current repository and generates an `ado.yaml` file at its root.

This file is the ADO self-declaration of a service — it describes the service in structured ADO format so that any agent running `index-domain` across multiple repos can read it directly, without scraping from scratch.

Think of `ado.yaml` as the service's identity card for AI agents.

---

## When to use

Run this skill inside a service repository when you want to:
- Register this service in an ADO domain index
- Make it readable by AI agents without full repository exploration
- Keep the service's ADO entry up to date as the codebase evolves

---

## Input

No arguments required. The skill operates on the current repository.

Optionally, the user may provide:
- `ownership_type` — `owner` | `internal` | `partner` (defaults to `owner`)
- `domain` — name of the domain this service belongs to

---

## Process

### Step 1 — Collect service context

Ask the user the following in a single message:

---

**Setting up index-service for this service.** A few questions before I start analyzing the code:

1. What is the service name? *(should match how it's referenced in other services)*
2. What does this service do? *(2–3 sentences: responsibility, users, business value)*
3. What is the ownership type? `owner` | `internal` | `partner`
4. What domain does this service belong to? *(e.g. `payments`, `ecommerce`)*
5. What is the criticality? `critical` | `high` | `medium` | `low`
6. Are there links to docs? *(README, AI_CONTEXT.md — I'll try to find them automatically)*

---

Wait for the answers. If any field is ambiguous, ask before proceeding.

---

### Step 2 — Analyze the repository

Scan the current repository for:

**A. HTTP routes / API surface**
- Look for router files, controller files, OpenAPI/Swagger specs
- Common patterns:
  - Go/Fiber: `app.Get`, `app.Post`, `v1.Get` in `main.go`, `routes.go`, `router.go`
  - NestJS: `@Get`, `@Post`, `@Controller` decorators
  - Express: `router.get`, `router.post`
  - OpenAPI: `paths:` in `swagger.yaml` / `openapi.yaml`
- Per route extract: `path`, `method`, description (from comments or docs), `headers`, `params`, `body` fields, store references

**B. Events (Kafka / async)**
- Look for topic names, producer calls, consumer decorators
- Common patterns:
  - Go: `kafka.Publish`, `topic :=`, `ProduceTopic`
  - NestJS: `@EventPattern`, `@EventSubscription`, `client.emit`
  - Config files: `topics:` blocks
- Per event extract: name, producer or consumer role, other services involved

**C. Data stores**
- Look for MongoDB collection names, Redis key prefixes, database config files
- Common patterns: `Collection("name")`, `db.collection`, `REDIS_PREFIX`, `keyPrefix`
- Extract: store type, collection names and purpose, access pattern per route

**D. Dependencies on other services**
- Look for HTTP client calls, service URLs in config/env, gRPC calls
- Map which routes call which external services

**E. Docs references**
- Check for `README.md`, `docs/AI_CONTEXT.md`, `docs/ARCHITECTURE.md`

**F. Check for existing service-snapshot.yaml**
- If present, use it as supplementary data for routes, events, stores, and tech stack
- The snapshot does not replace user-provided descriptions or UUID assignment

---

### Step 3 — Generate ado.yaml

Produce a single `ado.yaml` file at the root of the current repository.

The file describes **only this service** — no domain context, no team block. It is a self-contained service declaration that `index-domain` can merge into a full domain index.

Structure:

```yaml
# ADO service index — generated by index-service skill
# Keep this file updated as the service evolves.
# Read by AI agents and by index-domain when building domain indexes.

ado_version: v1
service: <service-name>
domain: <domain-name>
generated_at: <ISO8601 date>

ownership_type: owner        # owner | internal | partner
status: active               # active | deprecated | maintenance
criticality: high            # critical | high | medium | low
description: >
    <service description>

tech_stack:
    language: <language>
    framework: <framework>

url: <github repo url>
docs:
    readme: <url>
    ai_context: <url>

routes:
    - id: <v4 UUID>
      path: /v1/resource
      method: GET
      description: <what this endpoint does>
      headers:
        - authorization: string
      stores:
        - store: <store-name>
          collection: <collection>
          access: read

dependencies:
    - service: <service-name>
      routes:
        - <route UUID from target service, or TODO if unknown>

events:
    published:
        - name: <topic-name>
          description: <when and why this event is emitted>
          consumers:
              - <service-name>
    subscribed:
        - service: <service-name>
          events:
              - <topic-name>
          stores:
              - store: <store-name>
                collection: <collection>
                access: read_write
```

Key rules:
- Every route must have a unique **v4 UUID** `id`. Generate stable UUIDs — once assigned, never change them.
- `dependencies[].routes` references UUIDs from the **target** service. Use `TODO` if the target's UUID is unknown.
- `callers` are omitted — they are derived by `index-domain` during cross-service resolution.
- Mark unknown fields as `TODO` rather than guessing.

**YAML safety rules:**
1. Quote strings containing `: ` — e.g. `"Manages orders (ex: cart, checkout)"`
2. Quote strings containing `#`, `[`, `]`, `{`, `}`, `*`, `&`
3. Prefer block scalars (`description: >`) for long text

---

### Step 4 — Report

After writing the file:
- Routes found: N
- Events found: N published, N subscribed
- Stores found: N
- Fields marked TODO (requires manual review)
- Reminder: commit `ado.yaml` to the repository root so `index-domain` can find it

---

## How index-domain uses this file

When `index-domain` scrapes a repository, it checks for `ado.yaml` at the root **before** doing any scraping.

If found:
- Routes, events, stores, and descriptions are used directly
- UUIDs are preserved as-is
- Only cross-service relationships (callers, dependency UUID resolution) are resolved at domain level

If not found, `index-domain` falls back to `service-snapshot.yaml`, then to full scraping.

---

## Keeping ado.yaml up to date

Re-run this skill whenever:
- New routes are added or removed
- New events are published or subscribed
- Store access patterns change
- The service is deprecated or handed off to another team
